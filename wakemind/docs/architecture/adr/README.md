# Architecture Decision Records

Short documents capturing decisions that are expensive to reverse.

**Write an ADR when** a decision constrains future work, costs real money to
undo, or would otherwise be re-litigated by someone (including future us) who
doesn't have the context.

**Do not write one** for reversible implementation choices. Those belong in the
code and the PR description.

Status values: `Proposed` · `Accepted` · `Superseded by ADR-XXXX` · `Deprecated`

ADRs are append-only. To change a decision, write a new ADR that supersedes the
old one; never edit history. The trail is the point.
